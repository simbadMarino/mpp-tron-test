           TRON Charge Intent for HTTP Payment Authentication
                          draft-tron-charge-00

Abstract

   This document defines the "charge" intent for the "tron" payment
   method in the Payment HTTP Authentication Scheme
   [I-D.httpauth-payment].  It specifies how clients and servers
   exchange one-time TRC-20 token transfers on the TRON network.

   Four credential types are defined: type="permit2" (RECOMMENDED),
   where the client signs an off-chain Permit2 authorization and the
   server submits the transfer; type="authorization" (opt-in, only for
   tokens that implement transferWithAuthorization), where the client
   signs an off-chain transfer authorization and the server submits it
   to the token contract; type="transaction", where the client signs
   and the server broadcasts a TRC-20 transfer transaction; and
   type="hash" (optional fallback), where the client broadcasts the
   transaction itself and presents its transaction ID for server
   verification.

   As a TRON extension, a server can sponsor the network resources of
   a type="transaction" payment by delegating Energy and Bandwidth to
   the payer, so that a payer holding only TRC-20 tokens can pay.

   This specification covers TRC-20 token transfers only.  Native TRX
   and TRC-10 transfers are out of scope.

1.  Introduction

   HTTP Payment Authentication [I-D.httpauth-payment] defines a
   challenge-response mechanism that gates access to resources behind
   payments.  This document registers the "charge" intent for the
   "tron" payment method.

   TRON is a public blockchain whose virtual machine (the TVM) is
   largely compatible with the Ethereum Virtual Machine at the contract
   level: TRC-20 tokens [TRC-20] expose the same interface as ERC-20
   tokens, and contracts such as Permit2 [PERMIT2] can be deployed on
   it.  The network layer differs: TRON uses Base58Check addresses,
   protobuf-encoded transactions identified by the SHA-256 hash of
   their raw data, a reference-block mechanism instead of account
   nonces, and a resource model (Energy and Bandwidth) instead of gas.

   This specification inherits the shared request semantics of the
   "charge" intent from [I-D.payment-intent-charge].  It defines only
   the TRON-specific methodDetails, payload, and verification
   procedures.  It is derived from the EVM charge method
   [I-D.evm-charge] and keeps that document's structure and section
   numbering for Sections 1 to 10, so that the two can be compared
   section by section.

1.1.  Design Rationale

   The "evm" payment method cannot be reused for TRON: its addresses,
   its transaction format, its node interfaces and its gas model do
   not apply.  The payment flows, however, carry over unchanged.  This
   document therefore keeps the four credential types of
   [I-D.evm-charge] and their semantics, and replaces every
   network-specific element with its TRON counterpart.

   The protocol-level behavior (challenge, credential, receipt, errors)
   is defined by [I-D.httpauth-payment] and is identical for all
   payment methods.

1.2.  Client-Broadcast Fallback

   Some clients (custodial wallets, hardware signers) cannot hand off a
   signed-but-unbroadcast transaction.  For these cases, type="hash"
   allows the client to broadcast the transaction itself and present
   its transaction ID.  This mode provides weaker challenge binding and
   does not support splits or server-paid fees.  Servers SHOULD prefer
   type="permit2" or type="transaction" when possible.

1.3.  Credential Types

   This specification defines four credential types:

   *  *type="permit2" (RECOMMENDED)*: The client signs an off-chain
      TIP-712 [TIP-712] Permit2 authorization.  The server constructs
      and submits the on-chain transaction.  This is the preferred flow
      because:

      -  The client never interacts with the network directly

      -  The server pays the network resources (fee payer)

      -  Split payments are atomic via batch transfers

      -  externalId is cryptographically bound via witness data

   *  *type="authorization"*: The client signs an off-chain
      transferWithAuthorization message with the semantics of
      [EIP-3009].  The server submits it to the token contract.  This
      credential is available only for TRC-20 tokens that implement
      transferWithAuthorization.  At the time of writing no widely used
      TRC-20 token on TRON is known to do so (see Appendix C).

   *  *type="transaction"*: The client signs a complete TRC-20 transfer
      transaction.  The server broadcasts it.  The client pays the
      network resources, unless the server sponsors them
      (Section 11).

   *  *type="hash"*: The client signs and broadcasts a TRC-20 transfer
      transaction and presents its transaction ID for server
      verification.  This is the fallback for wallets that cannot hand
      off a signed-but-unbroadcast transaction.

   Servers that support Permit2 SHOULD advertise it as the preferred
   credential type.  Clients SHOULD prefer type="permit2" when
   available.

1.5.  Relationship to the Charge Intent

   This document inherits the shared request semantics of the "charge"

   specific methodDetails, payload, and verification procedures for the
   "tron" payment method.  The "session" intent for TRON is out of
   scope and is specified separately.

3.  Terminology

   TRC-20  The fungible token standard on TRON [TRC-20], equivalent to
      ERC-20.  Tokens expose transfer(address,uint256) and emit
      Transfer events on successful transfers.

   TRX  The native asset of the TRON network.  Out of scope as a
      payment currency in this document.

   Address  A TRON account or contract address.  On the wire it is the
      Base58Check encoding of a 21-byte value: the version byte 0x41
      followed by the 20-byte address (34 characters, starting with
      "T").  Inside ABI-encoded calldata, event logs and TIP-712 typed
      data the 20-byte form is used.

   Transaction ID  The SHA-256 hash of a transaction's raw_data, written
      as 64 hexadecimal characters.  It identifies the transaction on
      the network.

   Reference Block (TAPOS)  Every TRON transaction names a recent block
      (ref_block_bytes, ref_block_hash) and an expiration time.  A node
      accepts the transaction only if the reference block is on its
      chain and the expiration has not passed.  This binds a
      transaction to one network; TRON transactions carry no chain ID
      and no account nonce.

   Energy and Bandwidth  The network resources consumed by smart
      contract execution (Energy) and by transaction size (Bandwidth).
      An account obtains them by staking TRX, by receiving a delegation
      from another account, or pays for them by burning TRX up to the
      transaction's fee_limit.

   Resource Delegation  The transfer of the right to use Energy or
      Bandwidth, backed by staked TRX, from one account to another
      [TIP-467].  The delegating account can reclaim it.

   Account Activation  A TRON address exists as an account on the
      network only after it has been activated, for example by
      receiving TRX or by an AccountCreateContract transaction.  An
      address that has only received TRC-20 tokens may not be
      activated.

   Solidified Block  A block confirmed by more than two thirds of the
      network's block producers, after which it cannot be reverted.

   Permit2  Uniswap's token approval contract [PERMIT2].  Enables
      off-chain signed approvals for any TRC-20 token via the
      permitWitnessTransferFrom function (single and batch overloads).
      TRON has no canonical Permit2 address; deployments are listed per
      network (Section 4.2.4).

   TIP-712  TRON's standard for typed structured data hashing and
      signing [TIP-712], equivalent to EIP-712 [EIP-712] with TRON
      addresses encoded in their 20-byte form.

   Base Units  The smallest transferable unit of a token, determined by
      the token's decimal precision.  For example, USDT on TRON (6
      decimals) uses 1,000,000 base units per 1 USDT.

4.  Request Schema

   The request parameter in the WWW-Authenticate challenge contains a
   base64url-encoded JSON object.  The JSON MUST be serialized using
   JSON Canonicalization Scheme (JCS) [RFC8785] before base64url
   encoding, per [I-D.httpauth-payment].

4.1.  Shared Fields

     +=============+========+==========+=============================+
     | Field       | Type   | Required | Description                 |
     +=============+========+==========+=============================+
     | amount      | string | REQUIRED | Amount in base units        |
     |             |        |          | (stringified non-negative   |
     |             |        |          | integer)                    |
     +-------------+--------+----------+-----------------------------+
     | currency    | string | REQUIRED | TRC-20 token contract       |
     |             |        |          | address                     |
     +-------------+--------+----------+-----------------------------+
     | recipient   | string | REQUIRED | Recipient address           |
     +-------------+--------+----------+-----------------------------+
     | description | string | OPTIONAL | Human-readable payment      |
     |             |        |          | description                 |
     +-------------+--------+----------+-----------------------------+
     | externalId  | string | OPTIONAL | Merchant's reference (order |
     |             |        |          | ID, invoice number, etc.)   |
     +-------------+--------+----------+-----------------------------+

                                  Table 2

   Challenge expiry is conveyed by the expires auth-param in WWW-
   Authenticate per [I-D.httpauth-payment].  The request MUST NOT carry
   a separate expiry value.

   amount MUST contain only decimal digits, with no sign, decimal point
   or exponent.  Implementations MUST use exact integer arithmetic for
   amounts.

   Addresses in currency, recipient and every other address field of
   this document MUST be Base58Check-encoded TRON addresses (Section 3).
   Implementations MUST validate the checksum and the 0x41 version byte
   and MUST compare addresses by their decoded 20-byte value, not by
   string form.

   currency MUST be the address of a TRC-20 contract.  Native TRX and
   TRC-10 assets cannot be charged with this method.

4.2.  Method Details

    +=================+=========+==========+==========================+
    | Field           | Type    | Required | Description              |
    +=================+=========+==========+==========================+
    | chainId         | number  | REQUIRED | TRON chain ID (Section   |
    |                 |         |          | 4.2.1)                   |
    +-----------------+---------+----------+--------------------------+
    | permit2Address  | string  | see text | Permit2 contract address |
    |                 |         |          | on this network (no      |
    |                 |         |          | default; Section 4.2.4)  |
    +-----------------+---------+----------+--------------------------+
    | spender         | string  | see text | Address that submits     |
    |                 |         |          | Permit2 transfers for    |
    |                 |         |          | the server (Section 5.2) |
    +-----------------+---------+----------+--------------------------+
    | credentialTypes | array   | OPTIONAL | Ordered list of accepted |
    |                 |         |          | credential types         |
    +-----------------+---------+----------+--------------------------+
    | decimals        | number  | OPTIONAL | Token decimal precision  |
    |                 |         |          | (e.g., 6 for USDT).      |
    |                 |         |          | Display aid only.        |
    +-----------------+---------+----------+--------------------------+
    | splits          | array   | OPTIONAL | Additional payment       |
    |                 |         |          | splits (max 10)          |
    +-----------------+---------+----------+--------------------------+
    | resourceSponsor | boolean | OPTIONAL | Server sponsors the      |
    |                 |         |          | resources of a           |
    |                 |         |          | transaction credential   |
    |                 |         |          | (Section 11)             |
    +-----------------+---------+----------+--------------------------+

                                  Table 3

   permit2Address and spender are REQUIRED when "permit2" is an
   accepted credential type, which includes every challenge with
   splits.  Otherwise they MAY be omitted, so that a network without a
   Permit2 deployment can still use the other credential types.
   Permit2 signatures commit to the address that will call the Permit2
   contract (Section 5.2.1); the client cannot sign without spender.

   decimals, when present, MUST be used only for display.  It never
   changes the base-unit amount that is signed or verified.

   Clients MUST ignore unknown methodDetails fields, per
   [I-D.httpauth-payment].

4.2.1.  Chain Identification

   The chainId field is REQUIRED and identifies the TRON network.  The
   TRON chain ID is the value returned by the TVM's chainid opcode and
   used in TIP-712 domains; it equals the last four bytes of the
   network's genesis block ID, read as an unsigned integer.

          +==================+============+============+
          | Network          | chainId    | Hex        |
          +==================+============+============+
          | TRON Mainnet     | 728126428  | 0x2b6653dc |
          +------------------+------------+------------+
          | Nile Testnet     | 3448148188 | 0xcd8690dc |
          +------------------+------------+------------+
          | Shasta Testnet   | 2494104990 | 0x94a9059e |
          +------------------+------------+------------+

                                  Table 4

   Clients MUST reject, without signing or broadcasting anything,
   challenges whose chainId does not match a network they support.
   Servers MUST use a node of the network named by chainId, and SHOULD
   verify at startup that the node reports that chain.

4.2.2.  Credential Type Negotiation

   Servers MAY indicate accepted credential types via the
   credentialTypes field in methodDetails:

   Valid values: "permit2", "authorization", "transaction", "hash".

   If omitted, servers MUST accept "transaction" and SHOULD accept
   "hash".  Servers that support Permit2 SHOULD include "permit2" as the
   first entry to indicate preference.  Servers MUST only include
   "authorization" when the currency token is known to implement
   transferWithAuthorization.  Clients SHOULD use the first type in the
   list that they support.  Servers MUST reject a credential whose type
   is not accepted for the challenge.

   Resource sponsorship (Section 11) is not a credential type; it
   modifies type="transaction".

4.2.3.  Payment Splits

   The splits field enables a single charge to distribute payment across
   multiple recipients.  This is useful for platform fees, revenue
   sharing, and marketplace payouts.

   Splits REQUIRE type="permit2" credentials.  The Permit2 batch
   transfer mechanism ensures all transfers (primary + splits) execute
   atomically in a single on-chain transaction.  Servers MUST reject
   split requests fulfilled with type="transaction",
   type="authorization", or type="hash" credentials.  Servers MUST NOT
   issue splits on a network without a Permit2 deployment.

   Each entry in the splits array is a JSON object:

   +===========+========+==========+===================================+
   | Field     | Type   | Required | Description                       |
   +===========+========+==========+===================================+
   | recipient | string | REQUIRED | Address of split recipient        |
   +-----------+--------+----------+-----------------------------------+
   | amount    | string | REQUIRED | Amount in base units              |
   |           |        |          | for this recipient                |
   +-----------+--------+----------+-----------------------------------+
   | memo      | string | OPTIONAL | Human-readable label              |
   |           |        |          | (max 256 chars)                   |
   +-----------+--------+----------+-----------------------------------+

                                  Table 5

   The top-level amount represents the total the client pays.  The
   primary recipient receives the remainder: amount minus the sum of all
   split amounts.

   Constraints:

   *  The sum of splits[].amount MUST be strictly less than amount.
      Servers MUST NOT issue, and clients MUST reject, any request that
      violates this constraint.

   *  If present, splits MUST contain at least 1 entry.  Servers SHOULD
      limit splits to 10 entries.

   *  All transfers MUST target the same currency token.

   *  Address fields are compared by decoded 20-byte value, not by
      string form.

   The order of entries in splits is significant for verification.
   Clients MUST emit transfers in array order.  Servers MUST verify
   transferDetails[0] as the primary transfer and transferDetails[i+1]
   as splits[i].

   *Example:*

   {
     "amount": "1050000",
     "currency": "TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t",
     "recipient": "TLeN9QrXNSwqwniW6C48AaEPHZGtKyWeKm",
     "description": "Marketplace purchase",
     "methodDetails": {
       "chainId": 728126428,
       "permit2Address": "TTJxU3P8rHycAyFY4kVtGNfmnMH4ezcuM9",
       "spender": "TVrKLzFi2AVno1wxY3buk5NuTwwtPSGeXf",
       "credentialTypes": ["permit2"],
       "splits": [
         {
           "recipient": "TDZ7envevLByCdbKUrcAE7wPzV9E4jfVSj",
           "amount": "50000",
           "memo": "platform fee"
         }
       ]
     }
   }

   This requests a total payment of 1.05 USDT on TRON mainnet.  The
   platform receives 0.05 USDT and the primary recipient receives 1.00
   USDT.  Both transfers execute atomically via Permit2 batch.

4.2.4.  Permit2 Deployments

   TRON has no canonical, cross-network Permit2 address.  permit2Address
   therefore has no default value and MUST be present whenever
   "permit2" is offered (Section 4.2).  Clients SHOULD sign
   a Permit2 authorization only when permit2Address equals a deployment
   they know for the challenge's chainId, and implementations SHOULD
   ship such a list.  Deployments known at the time of writing:

     +==================+====================================+
     | Network          | Permit2 address                    |
     +==================+====================================+
     | TRON Mainnet     | TTJxU3P8rHycAyFY4kVtGNfmnMH4ezcuM9 |
     +------------------+------------------------------------+
     | Nile Testnet     | TEetQ5ohtKF5eAF9ec6jbvdTzcLDsB6jTs |
     +------------------+------------------------------------+
     | Shasta Testnet   | none known                         |
     +------------------+------------------------------------+

                                  Table 6

   Both listed deployments expose the standard Permit2 interface,
   including both overloads of permitWitnessTransferFrom, and their
   DOMAIN_SEPARATOR() equals the standard Permit2 TIP-712 domain (name

5.  Credential Schema

   The credential in the Authorization header contains a base64url-
   encoded JSON object per [I-D.httpauth-payment].

5.1.  Credential Structure

         +===========+========+==========+=======================+
         | Field     | Type   | Required | Description           |
         +===========+========+==========+=======================+
         | challenge | object | REQUIRED | Echo of the challenge |
         |           |        |          | from the server       |
         +-----------+--------+----------+-----------------------+
         | payload   | object | REQUIRED | TRON-specific payload |
         +-----------+--------+----------+-----------------------+
         | source    | string | see text | Payer identifier as a |
         |           |        |          | DID                   |
         +-----------+--------+----------+-----------------------+

                                  Table 7

   source is REQUIRED for type="permit2", where it identifies the
   token owner passed to the Permit2 contract, and OPTIONAL otherwise.
   When present it MUST use the did:pkh method [DID-PKH] with the
   "tron" namespace, the challenge chainId in decimal as the chain
   reference [CAIP-2] defined for the "tron" namespace [CAIP-TRON],
   and the payer's Base58Check address, for example:

   did:pkh:tron:728126428:TBrgfKc9vXVE3ctTvXiZpXYAT1uWAnU2KN

   Clients MUST emit the decimal form.  Following [CAIP-TRON],
   servers MUST accept a chain reference in the deprecated
   0x-prefixed hexadecimal form (for example
   did:pkh:tron:0x2b6653dc:...) and normalize it to decimal before
   any comparison.  Servers MUST reject a source whose normalized
   chain reference differs from the challenge chainId, and MUST
   compare addresses by their decoded 20-byte value.

   For server-submitted types the address recovered from the signature
   MUST equal the address in source.

5.2.  Permit2 Payload (type="permit2")

   The RECOMMENDED credential type.  The client signs an off-chain
   TIP-712 Permit2 authorization message.  The server constructs and
   submits the on-chain transaction from the spender address, paying
   the network resources.  The client never interacts with the network
   directly.

   This type requires a Permit2 deployment on the network
   (Section 4.2.4) and an active TRC-20 approval from the client to the
   Permit2 contract that covers the total amount (a one-time operation
   per token per network).  Before signing, clients MUST check their
   allowance and token balance; if either is insufficient they MUST NOT
   sign a permit2 credential and SHOULD use another accepted credential
   type or first send the approval themselves.

    +=================+========+==========+===========================+
    | Field           | Type   | Required | Description               |
    +=================+========+==========+===========================+
    | type            | string | REQUIRED | "permit2"                 |
    +-----------------+--------+----------+---------------------------+
    | permit          | object | REQUIRED | Permit2 permit data       |
    +-----------------+--------+----------+---------------------------+
    | transferDetails | array  | REQUIRED | Array of transfer details |
    +-----------------+--------+----------+---------------------------+
    | witness         | object | REQUIRED | Challenge binding witness |
    |                 |        |          | data                      |
    +-----------------+--------+----------+---------------------------+
    | signature       | string | REQUIRED | TIP-712 signature, 65     |
    |                 |        |          | bytes (r, s, v), 0x-      |
    |                 |        |          | prefixed hex              |
    +-----------------+--------+----------+---------------------------+

                                  Table 8

5.2.1.  Permit Object

   The permit object describes the token permissions:

    +===========+========+============================================+
    | Field     | Type   | Description                                |
    +===========+========+============================================+
    | permitted | array  | Array of { token, amount } objects.  One   |
    |           |        | entry per transfer (primary + each split). |
    +-----------+--------+--------------------------------------------+
    | nonce     | string | Permit2 nonce (stringified integer)        |
    +-----------+--------+--------------------------------------------+
    | deadline  | string | Unix timestamp (stringified integer)       |
    +-----------+--------+--------------------------------------------+

                                  Table 9

   The permitted array MUST always be an array, even for single
   transfers (length 1).  Each entry specifies:

     +========+========+============================================+
     | Field  | Type   | Description                                |
     +========+========+============================================+
     | token  | string | TRC-20 token address (MUST match currency) |
     +--------+--------+--------------------------------------------+
     | amount | string | Maximum transfer amount in base units      |
     +--------+--------+--------------------------------------------+

                                 Table 10

   The signed TIP-712 message is the Permit2 witness transfer type.  For
   a single transfer (permitted length 1) the primary type is
   PermitWitnessTransferFrom with permitted as one TokenPermissions;
   for a batch (permitted length > 1) it is
   PermitBatchWitnessTransferFrom with permitted as TokenPermissions[].
   In both cases the spender field of the message is
   methodDetails.spender, and the TIP-712 domain is:

   {
     "name": "Permit2",
     "chainId": <methodDetails.chainId>,
     "verifyingContract": <20-byte form of methodDetails.permit2Address>
   }

   Permit2 nonces are unordered: the client chooses any nonce it has
   not used with this Permit2 deployment.  deadline SHOULD NOT be later
   than the challenge expires.

5.2.2.  Transfer Details

   The transferDetails array MUST have the same length as permitted.
   Each entry specifies:

    +=================+========+=====================================+
    | Field           | Type   | Description                         |
    +=================+========+=====================================+
    | to              | string | Recipient address                   |
    +-----------------+--------+-------------------------------------+
    | requestedAmount | string | Exact transfer amount in base units |
    +-----------------+--------+-------------------------------------+

                                 Table 11

   The first entry corresponds to the primary recipient.  Subsequent
   entries (if any) correspond to split recipients in array order.
   Recipients and amounts in transferDetails are not covered by the
   Permit2 signature itself; they are bound to the challenge through
   the witness (Section 5.2.3) and verified by the server
   (Section 6.1).

5.2.3.  Witness Data (Challenge Binding)

   The Permit2 witness mechanism provides cryptographic binding between
   the payment authorization and the challenge.  When externalId is
   present in the challenge request, the client MUST include it in the
   TIP-712 witness struct.  When externalId is absent from the challenge
   request, PaymentWitness.externalId is the empty string ("").  The
   server MUST verify the witness matches before submitting the
   transaction.

   The witness type is defined as:

   struct PaymentWitness {
       bytes32 challengeHash;
       string externalId;
   }

   Where challengeHash is computed as:

   challengeHash = keccak256(abi.encodePacked(
       challenge.id,
       challenge.realm
   ))

   This binds the Permit2 signature to the specific challenge instance.
   The signature cannot be reused against a different challenge, even if
   the payment parameters are identical.

   The witness type string passed to the Permit2 contract is (one line,
   no whitespace other than the single spaces shown):

   PaymentWitness witness)PaymentWitness(bytes32 challengeHash,string
   externalId)TokenPermissions(address token,uint256 amount)

   The witness value passed to the contract is the TIP-712 struct hash:

   witness = keccak256(abi.encode(
       keccak256("PaymentWitness(bytes32 challengeHash,string
                  externalId)"),
       challengeHash,
       keccak256(bytes(externalId))
   ))

   Implementations MUST use exactly this type string when constructing
   the TIP-712 typed data.  The same witness is used by the single and
   the batch overload of permitWitnessTransferFrom().

5.2.4.  Server Behavior

   For single transfers (no splits, permitted length 1), the server
   calls the single overload of permitWitnessTransferFrom() on the
   Permit2 contract.

   For batch transfers (with splits, permitted length > 1), the server
   calls the batch overload of permitWitnessTransferFrom(), which takes
   arrays of TokenPermissions and transfer details.  (The batch call is
   an overload of the same function name; PermitBatchWitnessTransferFrom
   is only the name of its signed type.)  This executes all transfers in
   a single on-chain transaction; if any transfer fails, the entire
   batch reverts.

   The server submits from the spender address and pays the Energy and
   Bandwidth in both cases.  This is the natural fee sponsorship model
   for Permit2: the client signs only the off-chain authorization and
   the server handles all network interaction.

5.3.  Authorization Payload (type="authorization")

   Opt-in credential type for TRC-20 tokens that implement
   transferWithAuthorization with the semantics of [EIP-3009].  The
   client signs an off-chain transferWithAuthorization message per
   TIP-712.  The server submits it directly to the token contract,
   paying the network resources.  The client never interacts with the
   network directly.

   Unlike type="permit2", this type requires no prior token approval;
   the authorization mechanism is built into the token contract itself.

    +=============+========+==========+===============================+
    | Field       | Type   | Required | Description                   |
    +=============+========+==========+===============================+
    | type        | string | REQUIRED | "authorization"               |
    +-------------+--------+----------+-------------------------------+
    | from        | string | REQUIRED | Payer address                 |
    +-------------+--------+----------+-------------------------------+
    | to          | string | REQUIRED | Recipient address (MUST match |
    |             |        |          | challenge recipient)          |
    +-------------+--------+----------+-------------------------------+
    | value       | string | REQUIRED | Transfer amount in base units |
    |             |        |          | (MUST match challenge amount) |
    +-------------+--------+----------+-------------------------------+
    | validAfter  | string | REQUIRED | Unix timestamp; authorization |
    |             |        |          | not valid before this time    |
    |             |        |          | (stringified integer,         |
    |             |        |          | typically "0")                |
    +-------------+--------+----------+-------------------------------+
    | validBefore | string | REQUIRED | Unix timestamp; authorization |
    |             |        |          | not valid after this time     |
    |             |        |          | (stringified integer)         |
    +-------------+--------+----------+-------------------------------+
    | nonce       | string | REQUIRED | bytes32 nonce; MUST be set to |
    |             |        |          | challengeHash (see below)     |
    +-------------+--------+----------+-------------------------------+
    | signature   | string | REQUIRED | TIP-712 signature, 65 bytes,  |
    |             |        |          | 0x-prefixed hex               |
    +-------------+--------+----------+-------------------------------+

                                 Table 12

5.3.1.  Challenge Binding

   The [EIP-3009] nonce field is a bytes32 value chosen by the caller.
   This specification requires the nonce to be set to the
   challengeHash:

   nonce = keccak256(abi.encodePacked(
       challenge.id,
       challenge.realm
   ))

   This provides cryptographic challenge binding equivalent to the
   Permit2 witness mechanism.  The token contract enforces nonce
   uniqueness on-chain: a nonce that has been consumed cannot be
   reused, providing replay protection at the contract level.

5.3.2.  Constraints

   *  Splits are NOT supported.  Servers MUST reject
      type="authorization" credentials when the challenge includes
      splits.

   *  Servers MUST NOT advertise "authorization" in credentialTypes
      unless the currency token is known to implement
      transferWithAuthorization.

   *  validBefore SHOULD correspond to the challenge expires timestamp.

   *  to MUST match the challenge recipient.

   *  value MUST match the challenge amount.

5.4.  Transaction Payload (type="transaction")

   The client signs a complete TRC-20 transfer transaction targeting the
   currency contract.  The server broadcasts the transaction to the
   network.  The client pays the network resources, unless the
   challenge offers resource sponsorship (Section 11).

      +===========+========+==========+============================+
      | Field     | Type   | Required | Description                |
      +===========+========+==========+============================+
      | type      | string | REQUIRED | "transaction"              |
      +-----------+--------+----------+----------------------------+
      | signature | string | REQUIRED | Hex-encoded, protobuf-     |
      |           |        |          | serialized signed TRON     |
      |           |        |          | Transaction                |
      +-----------+--------+----------+----------------------------+

                                 Table 13

   The signature field contains a TRON Transaction message (raw_data
   and signature) serialized as protobuf and encoded as hexadecimal,
   in the form accepted by a node's broadcasthex interface.  The JSON
   form of a transaction returned by node APIs is not accepted.  The
   transaction MUST contain exactly one contract of type
   TriggerSmartContract that calls transfer(address,uint256) on the
   TRC-20 token specified in the challenge, with the challenge
   recipient and amount, a call_value of zero and no TRC-10 value.

   The client MUST sign a fully valid transaction: the reference block
   taken from the network named by chainId, an expiration in the
   future and not later than the challenge expires, and a fee_limit
   that covers the transfer.  Without resource sponsorship the payer
   account MUST hold the Energy and Bandwidth, or the TRX to burn, for
   the transfer.  The client MUST NOT broadcast the transaction itself.

   The transaction MAY be signed under the owner permission or under an
   active permission of the payer account (the contract's
   Permission_id), with as many signatures as that permission's
   threshold requires.  All signatures MUST be in place before the
   credential is sent, and the expiration limit above still applies,
   so signing by several parties has to finish before the challenge
   expires.

   Splits are NOT supported with type="transaction".  Servers MUST
   reject type="transaction" credentials when the challenge includes
   splits.

   *Example:*

   {
     "challenge": {
       "id": "kM9xPqWvT2nJrHsY4aDfEb",
       "realm": "api.example.com",
       "method": "tron",
       "intent": "charge",
       "request": "eyJ...",
       "expires": "2026-04-01T12:05:00Z"
     },
     "payload": {
       "signature": "0a8f010a02...signed transaction bytes...",
       "type": "transaction"
     },
     "source": "did:pkh:tron:728126428:TBrgfKc9...uWAnU2KN"
   }

5.5.  Hash Payload (type="hash")

   Optional fallback for clients that broadcast transactions themselves
   (e.g., custodial wallets, hardware signers).  The client broadcasts a
   TRC-20 transfer transaction to the network, pays its resources, and
   presents the transaction ID once the transaction is included.

          +=======+========+==========+=========================+
          | Field | Type   | Required | Description             |
          +=======+========+==========+=========================+
          | type  | string | REQUIRED | "hash"                  |
          +-------+--------+----------+-------------------------+
          | hash  | string | REQUIRED | Transaction ID (32      |
          |       |        |          | bytes, 64 hex           |
          |       |        |          | characters)             |
          +-------+--------+----------+-------------------------+

                                 Table 14

   TRON tooling usually shows transaction IDs without a 0x prefix.
   Servers MUST accept the ID with or without the prefix and in either
   letter case, and MUST normalize it (lowercase, no prefix) before
   any comparison or replay check.

   Constraints:

   *  Splits are NOT supported.  Servers MUST reject type="hash"
      credentials when the challenge includes splits.

   *  The client pays the network resources.

   *  The server cannot modify or retry the transaction.

   *  Weaker challenge binding than other types (see Section 10.4).

   *Example:*

   {
     "challenge": {
       "id": "kM9xPqWvT2nJrHsY4aDfEb",
       "realm": "api.example.com",
       "method": "tron",
       "intent": "charge",
       "request": "eyJ...",
       "expires": "2026-04-01T12:05:00Z"
     },
     "payload": {
       "hash": "1a2b3c4d5e6f7890...abcdef1234567890",
       "type": "hash"
     },
     "source": "did:pkh:tron:728126428:TBrgfKc9...uWAnU2KN"
   }

5.6.  Resource Model and Fee Payment

   TRON has no gas price.  A transaction consumes Bandwidth (for its
   size) and, when it executes a contract, Energy.  The sending account
   pays with Energy and Bandwidth it holds through staking or
   delegation, and burns TRX for any shortfall, up to the
   transaction's fee_limit.  A transaction that runs out of Energy
   within its fee_limit fails but is still recorded on-chain and still
   charged.

   Who pays is determined by the credential type and, for
   type="transaction", by resource sponsorship:

   +=================+==============+=================================+
   | Credential Type | Who Pays     | Mechanism                       |
   +=================+==============+=================================+
   | permit2         | Server       | Client signs off-chain; server  |
   |                 |              | submits from spender            |
   +-----------------+--------------+---------------------------------+
   | authorization   | Server       | Client signs off-chain; server  |
   |                 |              | submits to token contract       |
   +-----------------+--------------+---------------------------------+
   | transaction     | Client       | Client signs a full transaction |
   |                 |              | with a fee_limit                |
   +-----------------+--------------+---------------------------------+
   | transaction,    | Server       | Server delegates Energy (and    |
   | resourceSponsor |              | Bandwidth) to the payer before  |
   |                 |              | broadcasting (Section 11)       |
   +-----------------+--------------+---------------------------------+
   | hash            | Client       | Client broadcasts the           |
   |                 |              | transaction themselves          |
   +-----------------+--------------+---------------------------------+

                                 Table 15

   For type="permit2" and type="authorization", the client signs only
   an off-chain message; it never submits a transaction and therefore
   cannot pay.  The server MUST hold sufficient Energy, Bandwidth or
   TRX to cover these credential types and MUST set a bounded
   fee_limit on the transactions it submits.

   For type="transaction" without sponsorship and for type="hash", the
   client is responsible for the resources.  The server broadcasts or
   verifies the transaction but does not subsidize it.

   The challenge amount never includes or deducts network fees.  A
   server that pays the resources recovers them, if at all, through
   its pricing.

6.  Verification Procedure

   Upon receiving a request with a credential, the server MUST:

   1.  Decode the base64url credential and parse the JSON.

   2.  Verify that payload.type is present and is one of the credential
       types accepted for the challenge.

   3.  Verify the challenge binding per [I-D.httpauth-payment]: the
       challenge id proves that the server issued the challenge and
       that no echoed field (credential.challenge) differs from what
       was issued.  A server MAY do this statelessly, by recomputing an
       HMAC over the echoed parameters, or by looking up a stored
       challenge.  If the binding does not verify, reject the request.

   4.  Verify that the challenge has not expired and has not already
       been consumed by an accepted payment (Section 8).

   5.  If the challenge includes splits and payload.type is not
       "permit2", reject the request.  (Only Permit2 supports atomic
       batch transfers for splits.)

   6.  Proceed with type-specific verification:

       *  For type="permit2": see Section 6.1.

       *  For type="authorization": see Section 6.2.

       *  For type="transaction": see Section 6.3.

       *  For type="hash": see Section 6.4.

   Verification reads from the network but MUST NOT write to it.
   Network writes (submission, broadcast, delegation, activation) are
   part of settlement (Section 7, Section 11) and happen only after
   verification has succeeded.

6.1.  Permit2 Verification

   Before submitting, servers MUST verify:

   1.   The TIP-712 signature is valid over a message whose spender is
        methodDetails.spender, the account the server will submit
        from, and recovers to the address in source

   2.   The deadline has not passed

   3.   The signer has sufficient token balance for the total amount
        (primary + all splits)

   4.   The signer has sufficient Permit2 allowance on currency

   5.   witness.challengeHash matches the value derived from the
        challenge id and realm, and witness.externalId matches the
        request (empty string when absent)

   6.   permitted and transferDetails arrays have equal length

   7.   Each permitted[i].token matches currency

   8.   transferDetails[0].to matches recipient

   9.   transferDetails[0].requestedAmount matches the primary transfer
        amount (amount minus sum of splits, or amount if no splits)

   10.  For each split at index i (if present), transferDetails[i+1].to
        matches splits[i].recipient and
        transferDetails[i+1].requestedAmount matches splits[i].amount

   11.  The account permissions of the source address still authorize
        the key that derives to that address: that key alone meets
        the threshold of the owner permission, or of an active
        permission whose operations allow TriggerSmartContract.
        Otherwise the server rejects the credential with
        verification-failed (see Section 10.5)

   Servers SHOULD simulate the transfer with a constant (read-only)
   contract call, such as a node's triggerconstantcontract interface,
   before submitting, to detect failures without spending resources.

6.2.  Authorization Verification

   Before submitting, servers MUST verify:

   1.  The currency token implements transferWithAuthorization

   2.  The TIP-712 signature is valid and recovers to the from address

   3.  to matches the challenge recipient

   4.  value matches the challenge amount

   5.  nonce matches the expected challengeHash derived from the
       challenge id and realm

   6.  The authorization is currently valid: validAfter is before and
       validBefore is after the current time

   7.  The signer has sufficient token balance

   8.  The account permissions of the from address still authorize
       the key that derives to that address, as in step 11 of
       Section 6.1

   Servers SHOULD simulate the transfer with a constant contract call
   before submitting.

6.3.  Transaction Verification

   Before broadcasting, servers MUST verify:

   1.  Decode the protobuf Transaction from the hex in
       payload.signature.

   2.  Compute the transaction ID as SHA-256 of raw_data.

   3.  Verify that raw_data contains exactly one contract, of type
       TriggerSmartContract.

   4.  Verify that its contract_address matches currency and that
       call_value and any TRC-10 value are zero.

   5.  Verify that the calldata begins with the
       transfer(address,uint256) function selector (0xa9059cbb) and
       decodes, with no trailing data, to the challenge recipient and
       amount.

   6.  Read the permissions of the owner_address account and select
       the permission named by the contract's Permission_id (0 for
       owner, 2 or higher for an active permission).  Verify that each
       signature recovers, over the transaction ID, to a different key
       of that permission, that the weights of those keys reach the
       permission's threshold, and, for an active permission, that its
       operations allow TriggerSmartContract.

   7.  Verify that the expiration has not passed.

   8.  Verify that the transaction ID has not been consumed
       (Section 8).

   9.  Verify that the owner account exists on the network (is
       activated).  If it does not, reject the credential with
       verification-failed, unless the server performs account
       activation under Section 11.6.

   A TRON transaction carries no chain ID.  It is bound to one network
   by its reference block, which nodes of other networks reject.
   Servers MUST broadcast only to a node of the network named by
   chainId.

   Recovering a signature to owner_address is not sufficient: a key
   removed from the account's permissions still recovers to the
   address, and the node would reject the transaction on broadcast,
   after a sponsoring server had already delegated resources
   (Section 11).

   Accounts whose permissions require several signatures cannot use
   type="permit2" or type="authorization" (Section 10.5); they pay
   with type="transaction" or type="hash".

6.4.  Hash Verification

   For hash credentials, servers MUST:

   1.  Verify payload.hash is 32 bytes of hex and normalize it
       (Section 5.5)

   2.  Verify the normalized transaction ID has not been previously
       consumed (Section 8)

   3.  Fetch the transaction info by ID from the network

   4.  Verify the transaction is included in a block and its execution
       result is SUCCESS (Section 10.9)

   5.  Verify the transaction info contains a Transfer event (topic
       ddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef)
       where:

       *  The emitting contract matches currency

       *  The to parameter matches recipient

       *  The value parameter matches amount

   6.  Apply the confirmation policy (Section 7.5)

   7.  Mark the transaction ID as consumed

   Event logs on TRON give addresses in their 20-byte form; servers
   MUST compare them with the decoded 20-byte value of the challenge
   addresses.

7.  Settlement Procedure

   For every credential type the payment succeeds only when the
   settling transaction is included in a block, its execution result is
   SUCCESS (Section 10.9), and its Transfer event(s) match the expected
   transfers (Section 6.4, step 5).  For permit2 with splits, every
   expected transfer MUST have its own matching event.

7.1.  Permit2 Settlement

   Client                  Server               TRON Network
     |                        |                      |
     | (1) Authorization:     |                      |
     |     Payment <cred>     |                      |
     |  (Permit2 signature)   |                      |
     |----------------------->|                      |
     |                        | (2) Verify sig,      |
     |                        |     simulate         |
     |                        | (3) Submit permit-   |
     |                        |  WitnessTransfer-    |
     |                        |  From() from spender |
     |                        |--------------------->|
     |                        | (4) Transaction info |
     |                        |  (all transfers      |
     |                        |   atomic in 1 tx)    |
     |                        |<---------------------|
     | (5) 200 OK + Receipt   |                      |
     |<-----------------------|                      |

   For single transfers, the server calls the single overload of
   permitWitnessTransferFrom().  When splits are present, the server
   calls the batch overload, executing the primary transfer and all
   splits atomically in a single transaction.

   Client                  Server               TRON Network
     |                        |                      |
     | (1) Authorization:     |                      |

     |                        | (2) Verify sig       |
     |                        | (3) Submit transfer- |
     |                        |  WithAuthorization() |

7.5.  Confirmation Requirements

   Servers MUST wait until the settling transaction is included in at
   least one block with execution result SUCCESS before returning a
   Payment-Receipt header.

   TRON produces a block about every three seconds.  A block becomes
   solidified, and can no longer be reverted, once more than two thirds
   of the block producers have built on it, which typically takes about
   one minute.  Servers SHOULD NOT assume a fixed confirmation latency.

   By default, servers return the receipt once the transaction is
   included in the first block with execution result SUCCESS.  Servers
   MUST offer a configuration option to wait instead until that block
   is solidified, and MAY read solidified data through a node's
   solidity interface.

   A server that waits for a transaction it broadcast MUST bound the
   wait.  When the transaction's expiration has passed and the server
   has confirmed that it was not included, the transaction can no
   longer be included and the server MUST treat the payment as failed.
   Until then the outcome is unknown and the replay reservations of
   Section 8 stay in place.

7.6.  Receipt Generation

   Upon successful settlement, servers MUST return a Payment-Receipt
   header per [I-D.httpauth-payment].  Servers MUST NOT include a
   Payment-Receipt header on error responses; failures are communicated
   via HTTP status codes and Problem Details [RFC9457].

   The receipt payload:

       +=============+========+====================================+
       | Field       | Type   | Description                        |

       +-------------+--------+------------------------------------+

   The reference MUST resolve, on the network named by chainId, to the
   transaction that paid.

8.  Replay Protection

   Each challenge id MUST be single-use [I-D.payment-intent-charge],
   and each payment proof MUST be accepted at most once, under any
   challenge.  Servers therefore track two identifiers per credential:
   the challenge id, and a proof token that depends on the credential
   type:

   *  *type="permit2"*: The combination of signer address and Permit2
      nonce.  The nonce is also consumed on-chain by the Permit2
      contract.

   *  *type="authorization"*: The combination of signer address and
      authorization nonce.  The nonce is also consumed on-chain by the
      token contract itself.

   *  *type="transaction"* and *type="hash"*: The normalized
      transaction ID (SHA-256 of raw_data).  Both types use the same
      key, so that a transaction the server broadcast for a
      type="transaction" credential cannot later be presented again as
      type="hash".

   Transaction IDs MUST be normalized (lowercase hex, no prefix) before
   they are checked or stored, so that one transaction cannot be
   presented twice in different spellings.

   Before any settlement side effect (submission, broadcast, resource
   delegation or account activation), and before accepting a
   transaction the client broadcast, the server MUST atomically reserve
   both identifiers.  A credential whose challenge id or proof token is
   already reserved or consumed MUST be rejected (Section 9).

   After verified settlement, the server MUST atomically record both
   identifiers as consumed before delivering the resource.  A definitive
   failure before payment releases the reservation.  While the outcome
   of a settlement is unknown, for example after a timeout, both
   identifiers MUST stay reserved until the server has determined the
   outcome (Section 7.5).

   Concurrent requests that share either identifier MUST result in at
   most one settlement and one resource delivery.  Reservations and
   consumed entries MUST be shared by all server instances and MUST
   survive restarts, so that a pending settlement can be reconciled by
   its transaction ID.  A consumed challenge id MAY be removed once the
   challenge can no longer be presented as valid.  Consumed transaction
   IDs SHOULD be kept without expiry, because a transaction ID stays
   valid on-chain forever.

9.  Error Responses

   Servers MUST use the problem types defined in
   [I-D.httpauth-payment] and SHOULD include a response body conforming
   to Problem Details [RFC9457] with Content-Type:
   application/problem+json.  The detail field SHOULD contain a human-
   readable description of the specific failure, for example that the
   execution result was REVERT or that the payer account is not
   activated.  Error details MUST NOT be placed in WWW-Authenticate
   parameters, and no error response includes a Payment-Receipt
   header (Section 7.6).

   Every 402 response MUST carry a fresh WWW-Authenticate: Payment
   challenge per [I-D.httpauth-payment].  For this method, servers
   classify failures as follows:

10.  Security Considerations

10.1.  Transport Security

   All communication MUST use TLS 1.2 or higher per
   [I-D.httpauth-payment].  Credentials MUST only be transmitted over
   HTTPS connections.

10.2.  Transaction Replay

   A TRON transaction is bound to one network by its reference block
   and is valid only until its expiration.  A node rejects a
   transaction whose ID it has already seen.  Permit2 and authorization
   signatures include the chain ID in the TIP-712 domain and consume
   nonces on-chain.  The expires auth-param limits the temporal window
   for credential use, and the server's consumed set (Section 8)
   prevents a credential from being accepted twice.

10.3.  Amount Verification

   Clients MUST parse and verify the request payload before signing:

   1.  Verify amount is reasonable for the service

   2.  Verify currency is the expected token address

   3.  Verify recipient is controlled by the expected party

   4.  Verify chainId matches the expected network

   5.  If splits are present, verify the sum of split amounts is
       strictly less than amount and all split recipients are expected

   6.  For type="permit2", verify that permit2Address is a known
       deployment for chainId (Section 4.2.4)

   Clients SHOULD present each split recipient and amount to the user
   and SHOULD make payments automatically only within an explicit
   policy, such as a maximum amount per payment and a list of allowed
   tokens and networks.  Clients MUST NOT pay automatically when the
   recipient or any split recipient is neither expected by the
   application for the resource nor explicitly confirmed by the user.

10.4.  Hash Credential Binding

   Hash credentials (type="hash") and transaction credentials
   (type="transaction") provide weaker challenge binding than Permit2
   credentials.  The server verifies that a payment matching the
   challenge terms exists on-chain, but cannot prove the payment was
   created for a specific challenge instance.

   By contrast, type="permit2" and type="authorization" credentials
   include a challengeHash (in the TIP-712 witness data for Permit2, or
   as the on-chain nonce for authorization), cryptographically binding
   the signature to the specific challenge id and realm.  This prevents
   signature reuse across challenges, even if payment parameters are
   identical.  This is a key reason off-chain signature types are
   preferred.

   Servers MAY mitigate this by:

   *  Requiring unique externalId values per challenge

   *  Preferring type="permit2" or type="transaction" in credentialTypes

   *  Restricting type="hash" to low-value transactions

10.5.  Permit2-Specific Risks

   *Allowance Prerequisite*: Permit2 requires a TRC-20 approve() to the
   Permit2 contract.  Clients should understand they are granting
   approval to a third-party contract.  Because TRON has no canonical
   Permit2 address, an attacker-controlled challenge could name a
   malicious contract as permit2Address; clients MUST NOT approve, and
   SHOULD NOT sign for, a contract that is not a known deployment for
   the network.

   *Nonce Management*: Permit2 nonces are consumed on-chain.  If a
   server fails to submit a Permit2 credential, the nonce remains
   unconsumed and the client can reuse it.  Servers MUST handle an
   already-consumed nonce as a normal verification failure.

   *Spender*: The client signs for the spender named in the challenge.
   Only that address can execute the transfer, which prevents a third
   party that intercepts the credential from submitting it.

   *Account Permissions*: TRON accounts can replace the key that
   controls them through account permissions, for example to rotate a
   compromised key or to require multiple signatures.  Nodes enforce
   these permissions only for transactions.  Permit2 verifies the
   off-chain signature with ecrecover, which returns the address
   derived from the signing key and ignores account permissions.  The
   original key of an address therefore remains able to sign Permit2
   transfers after it was removed from the account's permissions, for
   every token on which the account has an outstanding approval to
   Permit2.  The check in step 11 of Section 6.1 prevents a server
   from executing such a transfer, but it cannot prevent a direct call
   to Permit2.  Holders who change their account permissions SHOULD
   revoke their approvals to Permit2 (approve with amount zero), which
   the new keys can do.  Invalidating Permit2 nonces does not help,
   because the old key can sign with any unused nonce.  The same
   applies to the authorization credential type (step 8 of Section
   6.2), where no approval is needed: a removed key can sign
   authorizations for the whole balance of a token that implements
   transferWithAuthorization, and revoking is not possible.

10.6.  Fee Payer Risks

   With type="permit2" and type="authorization", the server pays the
   network resources on every settlement, including for transactions
   that fail on-chain.  This creates financial risk:

   *Denial of Service*: Malicious clients could submit credentials that
   fail on-chain, causing the server to pay without receiving payment.
   Mitigations:

   *  Simulate transfers with a constant contract call before
      submitting

   *  Rate limit per client address and IP

   *  Verify client token balance and allowance before submitting

   *  Require client authentication before accepting credentials

   *Resource Exhaustion*: Servers MUST monitor their Energy, Bandwidth
   and TRX balance and MUST stop offering server-paid credential types
   when they cannot cover a settlement.

   The Energy cost of a TRC-20 transfer varies with the token contract,
   with whether the recipient already holds the token, and with the
   network's dynamic energy parameters for heavily used contracts.
   Servers SHOULD factor this into pricing and SHOULD set fee_limit
   with margin above a simulated estimate.

10.7.  Split Payment Risks

   *Recipient Transparency*: Clients SHOULD present each split recipient
   and amount so the user can verify the payment distribution.  Clients
   SHOULD highlight when the primary recipient receives a small
   remainder relative to the total amount.

   *Batch Failure*: With Permit2 batch transfers, splits are atomic:
   all succeed or all revert.  A failure in any split causes the entire
   payment (including the primary transfer) to revert.  Servers SHOULD
   simulate the batch with a constant contract call before submitting
   to detect failures early.

10.8.  Node Trust

   Servers rely on their TRON node for transaction data.  A compromised
   or faulty node could return fabricated data.  Servers SHOULD use
   trusted node providers or run their own nodes, and MUST treat node
   errors, timeouts and inconsistent answers as verification failure,
   never as success.

10.9.  Execution Result of Included Transactions

   Unlike a rejected broadcast, a TRON transaction that fails during
   execution (for example with result REVERT, OUT_OF_ENERGY or
   OUT_OF_TIME) is still included in a block, has a valid transaction
   ID and still costs its sender resources.  Inclusion alone therefore
   proves nothing.  Servers MUST check the execution result in the
   transaction info and MUST accept a transaction only when the result
   is SUCCESS and the expected Transfer event is present.  A failed
   result is definitive; servers MUST NOT keep polling for a change.

11.  Resource Sponsorship (TRON Extension)

   This section defines an extension that has no counterpart in
   [I-D.evm-charge].  Servers and clients MAY implement it.

11.1.  Overview

   Many TRON users hold TRC-20 tokens, most often USDT, but little or
   no TRX, and therefore cannot pay the Energy for a token transfer.
   On TRON it is common practice for another account to delegate
   Energy and Bandwidth to such users [TIP-467].

   With resource sponsorship, the server delegates the resources a
   type="transaction" payment needs to the payer's account just before
   broadcasting the client-signed transfer, and reclaims them
   afterwards.  The payer signs the same transfer as without
   sponsorship and pays only the token amount.

   Sponsorship does not change the credential: it remains
   type="transaction" with the payload of Section 5.4.  It changes only
   which account provides the resources.

11.2.  The resourceSponsor Field

   methodDetails.resourceSponsor is an OPTIONAL boolean.  When true, the
   server will provide the Energy and Bandwidth for a type="transaction"
   credential by resource delegation.

   *  Servers MUST set resourceSponsor to true only when "transaction"
      is an accepted credential type, sponsorship is configured, and
      the server currently has the resources to sponsor.

   *  resourceSponsor does not affect amount, the other credential
      types, or splits.  Splits still require type="permit2".

   *  A client that does not implement this extension ignores the
      field (Section 4.2) and pays its own resources; the payment
      remains valid.

11.3.  Client Behavior

   Under a challenge with resourceSponsor true, a client MAY sign a
   type="transaction" credential without holding the Energy and
   Bandwidth for the transfer.  The client MUST still sign a fully
   valid transaction (Section 5.4), including a fee_limit, and SHOULD
   set its expiration late enough to leave the server time for the
   sponsorship steps of Section 11.4 (at least several blocks), while
   not later than the challenge expires.

11.4.  Server Procedure

   For a type="transaction" credential under a challenge with
   resourceSponsor true, the server MUST, in order:

   1.  Perform the verification of Section 6 and Section 6.3, including
       the replay check (Section 8).

   2.  Verify that the remaining time before the transaction's
       expiration covers the following steps; otherwise reject the
       credential without spending any resources.

   3.  Simulate the transfer with a constant contract call to confirm
       it would succeed and to estimate the Energy it needs, and read
       the payer's available Bandwidth.  The Energy of a TRC-20
       transfer depends on whether the recipient already holds the
       token; the simulation returns the value for the actual
       recipient.

   4.  If the payer account is not activated, activate it under
       Section 11.6 if the server allows activation, and wait for that
       transaction to be included; otherwise reject the credential.

   5.  Delegate Energy, and Bandwidth if the payer's available
       Bandwidth does not cover the transaction size, to the payer
       address (Section 11.5), and wait until the delegation is
       included.

   6.  Broadcast the client-signed transaction unchanged and complete
       settlement as in Section 7.3 and Section 7.5.

   7.  Reclaim the delegation (Section 11.5).

   Sponsored payments for the same payer address MUST be processed one
   at a time, so that concurrent credentials never cause parallel
   activations or delegations to one account.

   Client                  Server               TRON Network
     |                        |                      |
     | (1) Authorization:     |                      |
     |     Payment <cred>     |                      |
     |  (signed transaction)  |                      |
     |----------------------->|                      |
     |                        | (2) Verify, replay   |
     |                        |     check, simulate  |
     |                        |<-------------------->|
     |                        | (3) Activate payer   |
     |                        |     (only if allowed)|
     |                        |--------------------->|
     |                        | (4) Delegate Energy  |
     |                        |     to payer         |
     |                        |--------------------->|
     |                        | (5) Broadcast tx     |
     |                        |     unchanged        |
     |                        |--------------------->|
     |                        | (6) Transaction info |
     |                        |<---------------------|
     | (7) 200 OK + Receipt   |                      |
     |<-----------------------|                      |
     |                        | (8) Reclaim          |
     |                        |     delegation       |
     |                        |--------------------->|

11.5.  Delegation Bounds and Reclaim

   *  The server MUST NOT delegate more Energy than the simulated
      estimate plus a bounded margin, and SHOULD enforce a configured
      maximum per payment.

   *  The server MUST delegate without a lock period, so that the
      delegation can be reclaimed immediately.

   *  The server MUST reclaim the delegation after the payment
      succeeds, fails or times out.  Reclaiming SHOULD NOT delay the
      Payment-Receipt.

   *  A server MUST reclaim delegations left outstanding by an
      interruption, such as a restart, as soon as it resumes.

   Reclaiming returns the delegated stake at once, but Energy the
   payer consumed returns to the server's account as used Energy and
   recovers over 24 hours.  A server's daily sponsorship capacity is
   therefore bounded by its stake, and servers SHOULD stop offering
   resourceSponsor when the remaining resources cannot cover a
   payment.

   A payer's free daily Bandwidth covers about two TRC-20 transfers,
   but may already have been used; the server therefore checks the
   payer's available Bandwidth rather than assuming it.

11.6.  Account Activation

   Resource delegation to an address that is not yet an activated
   account does not succeed.  A server MAY activate such an address,
   subject to the following rules:

   *  Account activation MUST be disabled unless the server operator
      enables it explicitly.

   *  When enabled, the server MUST activate an address only for a
      sponsored payment that has passed every other check, including
      the replay check and the simulation of Section 11.4.

   *  The server SHOULD activate with an AccountCreateContract
      transaction of account type Normal, which creates the account
      without transferring TRX to the payer.  The server MUST read the
      account creation fee (1 TRX at the time of writing) from the
      network's chain parameters rather than assume a fixed value.

   *  The server MUST NOT activate when the payment amount is below a
      configured minimum, or when a configured activation budget for
      the current period is spent.  It then rejects the credential as
      in Section 6.3.

   Activation cannot be reversed.  Its fee is a permanent cost to the
   server, which is why it is disabled by default.

11.7.  Error Handling

   *  A payer account that is not activated, when the server does not
      or may not activate it, yields verification-failed with a detail
      saying so.

   *  A failed simulation, delegation or activation yields
      verification-failed, and nothing is broadcast.

   *  When the server's delegation resources or activation budget are
      temporarily exhausted, it SHOULD stop offering resourceSponsor in
      new challenges and SHOULD use Retry-After where a retry makes
      sense.

   *  A failed sponsored payment never leaves a delegation in place
      (Section 11.5).

11.8.  Security Considerations

   *Delegated resources belong to the payer*: Between delegation and
   broadcast, the delegated Energy and Bandwidth can be used by the
   payer's account for any transaction.  A malicious payer can, for
   example, move its tokens away before the server broadcasts the
   payment, so that the payment fails after the server has paid for
   the delegation and possibly an activation.  This risk cannot be
   removed, only bounded.  Type="permit2", where the server executes
   the transfer itself, has no such exposure and remains the preferred
   server-paid type.

   Servers MUST bound what a failed sponsored payment can cost them: at
   most one activation fee and the delegation of Section 11.5 per
   attempt, with sponsored attempts rate limited per payer address and
   IP, and activations limited separately.  Servers SHOULD stop
   sponsoring addresses or IP addresses whose sponsored payments
   repeatedly fail after delegation.

   *Activation abuse*: An attacker can create fresh addresses at no
   cost.  The minimum payment amount and the activation budget of
   Section 11.6 limit how much activation fees such an attacker can
   cause.

   *Expiration*: Sponsorship adds at least two block intervals before
   the broadcast.  A server that starts spending on a transaction close
   to its expiration can pay for a payment that can no longer settle;
   the check in step 2 of Section 11.4 prevents this.

   *3.  Server actions on the network (Section 11.4):*

   1.  Verify the transaction and simulate the transfer; the estimate
       is E Energy.

   2.  Payer account is activated: no activation needed.

   3.  Delegate at most E plus margin Energy to

       result SUCCESS and a matching Transfer event.

   5.  Return 200 with a receipt whose reference is the client
       transaction's ID; then reclaim the delegation.

   The payer's TRX balance is unchanged by the payment.

Appendix C.  Open Issues

   This appendix lists questions to resolve before publication.  It is
   to be removed by the RFC Editor.

   1.   Transaction ID and hash prefix convention: this document
        accepts transaction IDs with or without a 0x prefix and
        normalizes them to lowercase hex without prefix.

   2.   Broadcast of a transaction the node already knows (the client
        also broadcast it): reject, or verify it as type="hash".

   3.   Behavior while a settlement outcome is unknown (timeout):
        response code, and whether the client may retry the same
        credential.

   4.   type="authorization": no widely used TRC-20 token on TRON is
        known to implement transferWithAuthorization.  The type may be
        removed from this method or kept for future tokens.

   5.   Witness type string: the text rendering of [I-D.evm-charge]
        shows a space after the comma in "bytes32 challengeHash,
        string externalId", which TIP-712 and EIP-712 type encoding do
        not allow.  The string in Section 5.2.3 omits it.  Both methods
        should use the same string.

   6.   spender: [I-D.evm-charge] does not carry the Permit2 spender in
        the challenge, although the Permit2 signature commits to it.
        This document adds methodDetails.spender; the EVM method
        should be aligned.

   7.   Permit2 deployments: the listed addresses need verified source
        code; the two deployments are functionally identical but not
        byte-identical.

   8.   Resource sponsorship: field name and shape (boolean or an
        object with limits); delegation from the server's own stake
        versus a resource rental provider; activation by
        AccountCreateContract only, or also by TRX transfer.
